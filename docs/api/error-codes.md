# 🎫 错误码全表（Error Codes）

> 💻 代码实现：`server/at-common/.../result/ErrorCode.java`（本文档与枚举保持一致，Java 为准）。
> 📦 返回规则：无论 HTTP 状态如何，响应体恒为 `Result{code,message,data,traceId}`；前端以 `body.code` 为业务主判据。

## 🧭 一、编号分段

| 段 | 域 | HTTP 特征 |
| --- | --- | --- |
| `0` | 成功 | 200 |
| `1xxx` | 认证授权（含权限申请 / 授权冲突） | 401 / 403 / 400 · 200（流程提示） |
| `2xxx` | 参数校验 | 400 |
| `4xxx` | 文件 / 传输 | 200（分支）· 400 · 404 · 409 · 410 · 413 · 415 · 429 |
| `5xxx` | 系统异常 | 500 / 502 |

## 🗂️ 二、处理策略分类（按具体情况具体分析）

> 同一个 HTTP 状态可能对应完全不同的前端行为，因此**按「前端该做什么」**而非按数字分段划分策略。
> 下表策略代号将贯穿后续每张错误码表（「策略」列）与 `ErrorCode` 枚举注释，前端可据此写统一拦截器。

| 策略 | 名称 | 判定特征 | 前端标准动作 | 是否可原样重放 |
| --- | --- | --- | --- | --- |
| **A** | 成功 | `code=0` | 读取 `data` 正常渲染 | — |
| **B** | 流程分支 | `code≠0` 但 HTTP 200 | **不提示错误**，按 `data` 走业务分支（进入上传 / 按清单续传 / 直接访问 / 跳待办） | 是（由分支逻辑决定） |
| **C** | 凭证失效 | HTTP 401 | `1002` → 静默 refresh 后重放**一次**；其余 → 跳登录并清空令牌 | 仅 `1002` 可（且仅一次） |
| **D** | 拒绝且不跳登录 | HTTP 403 | 就地提示（无权限 / 已锁定 / 已禁用 / 提取码错误），**禁止**引导登录 | 否 |
| **E** | 请求需修正 | HTTP 400 / 404 / 413 / 415 | 定位到具体字段或资源后提示；修正后由用户重新发起 | 否（部分可重试，见 §四） |
| **F** | 状态失效 / 冲突 | HTTP 409 / 410 | 提示「状态已变化 / 已失效」，刷新列表或任务状态后重试 | 否（须先刷新状态） |
| **G** | 限流 / 锁定 | HTTP 429 | 提示被限流或已锁定，按退避策略（指数退避 / 等待解锁时刻）重试 | 是（退避后） |
| **H** | 系统兜底 | HTTP 500 / 502 | 统一提示「系统繁忙，请稍后重试」并展示 `traceId` 供上报 | 视接口幂等性而定 |

> ⚠️ **前端红线**：`5xxx` 与 `B` 类以外的错误，**禁止把服务端 `message` 当技术细节展示**；
> `message` 是给用户看的文案，技术排查一律用 `traceId`。

## ✅ 三、错误码明细

### 0：成功（策略 A）

| code | 枚举名 | HTTP | 策略 | 中文提示 | 说明 / 前端行为 |
| --- | --- | --- | --- | --- | --- |
| 0 | `SUCCESS` | 200 | A | 成功 | 正常返回，读取 `data` |

### 🔐 1xxx：认证授权

| code | 枚举名 | HTTP | 策略 | 中文提示 | 触发场景 / 前端行为 |
| --- | --- | --- | --- | --- | --- |
| 1001 | `NOT_LOGIN` | 401 | C | 未登录或登录已过期 | 未携带 token 访问受保护接口；跳登录 |
| 1002 | `TOKEN_EXPIRED` | 401 | C | 登录态已过期，请重新登录 | access token 过期；**静默**用 refresh token 换新并重放一次（仅一次，避免死循环） |
| 1003 | `NO_AUTH` | 403 | D | 无操作权限 | 已登录但 RBAC 无权限点 / 数据范围不足；提示无权限**不跳登录** |
| 1004 | `ACCOUNT_LOCKED` | 403 | D | 账号已锁定，请联系管理员 | 多次输错密码等触发锁定；提示联系管理员 |
| 1005 | `ACCOUNT_DISABLED` | 403 | D | 账号已被禁用，请联系管理员 | 账号被停用 / 冻结；提示联系管理员 |
| 1006 | `TOKEN_INVALID` | 401 | C | 登录态无效，请重新登录 | 伪造 / 签名错误 / 已吊销 token；refresh 失败时跳登录 |
| 1007 | `BAD_CREDENTIALS` | 401 | C | 账号或密码错误 | 登录鉴权失败（不区分“账号不存在”与“密码错误”）；清空密码框 |
| 1008 | `GRANT_ALREADY_ACTIVE` | 200 | B | 你已拥有该资源的有效授权 | 申请冲突校验命中：同资源已有生效授权；**流程提示码**，`data` 附现有授权信息，前端引导直接访问 |
| 1009 | `APPLICATION_DUPLICATE` | 200 | B | 您已有进行中的申请，请勿重复提交 | 申请冲突校验命中：同资源已有在审申请；**流程提示码**，`data` 附在审申请单 ID，前端跳转待办 |
| 1010 | `REASSIGN_INVALID` | 400 | E | 转审目标审批人无效或无权审批该资源 | 审批转审时目标审批人不存在 / 无权审批该资源；提示后重新选择审批人 |
| 1011 | `APPROVAL_STATE_ERROR` | 409 | F | 当前审批状态不允许该操作 | 审批 / 驳回 / 转审 / 撤销时状态机校验失败（典型：单据已被他人处理，CAS 影响行数 ≠ 1）；刷新单据状态后按新状态重试，**禁止原样重放** |
| 1012 | `CHAT_NOT_GROUP_MEMBER` | 403 | D | 你不是该群组成员，无法参与该群聊 | 群聊**发送或拉取历史**时当前用户不在 `sys_group_member` 内；**不跳登录**，提示后返回会话列表（退群后仍能读历史会成为越权读通道，故读写同校验） |
| 1013 | `CHAT_TARGET_INVALID` | 400 | E | 会话目标无效 | 单聊发给自己 / 目标用户不存在或已注销 / 群组不存在或已解散 / 群成员数超投递上限；修正目标后重新发起 |
| 1014 | `CHAT_MESSAGE_TYPE_INVALID` | 400 | E | 消息类型不允许用于会话 | 会话消息 `messageType` 传了 `0`（系统通知体）；会话只承载 `1`-文本 / `2`-文件传输 / `3`-审批结果三类 |
| 1015 | `USER_NOT_FOUND` | 404 | E | 用户不存在 | 用户详情 / 编辑 / 停用 / 删除时目标用户不存在或已被逻辑删除；提示后刷新用户列表 |
| 1016 | `USERNAME_CONFLICT` | 409 | F | 登录账号已被占用 | 建号 / 改名命中 `uk_username`（**含已逻辑删除的占位行**——逻辑删除行仍占名，故查重必须含删除行，否则会撞唯一键抛 500）；换账号名重试 |
| 1017 | `EMAIL_CONFLICT` | 409 | F | 邮箱已被占用 | 邮箱在**存活行**中已存在（删除行的邮箱可被复用，与账号名口径刻意不同）；换邮箱重试 |
| 1018 | `ROLE_NOT_FOUND` | 404 | E | 角色不存在 | 角色详情 / 编辑 / 删除 / 授权时目标角色不存在；刷新角色列表 |
| 1019 | `ROLE_CODE_CONFLICT` | 409 | F | 角色编码已存在 | 创建 / 改名角色时 `code` 重复（含已逻辑删除行，同 `uk_role_code` 口径）；换编码重试 |
| 1020 | `BUILT_IN_ROLE_PROTECTED` | 403 | D | 内置角色不允许删除或修改数据范围 | 对内建 `SUPER_ADMIN` / `AUDITOR` / `DEPT_ADMIN` / `USER` 执行删除，或试图改写其 `data_scope`；**就地提示不跳登录**，仅允许改名称 / 描述 |
| 1021 | `AUDITOR_PERM_LOCKED` | 403 | D | 审计员角色权限已锁定，不允许变更 | 对 `AUDITOR` 的权限集做任何增删——审计员若能改权限即可为自己扩权，「审计员能不能看审计」不能由被审计者自决；提示后关闭授权弹窗 |
| 1022 | `ROLE_IN_USE` | 409 | F | 角色仍被用户使用，无法删除 | 删除时 `sys_user_role` 仍有存活关联行；**先解除分配再删除**，提示可直接跳「用户分配角色」 |
| 1023 | `SELF_OPERATION_FORBIDDEN` | 403 | D | 不能对自己执行该操作 | 对**自己**停用 / 删除 / 重置口令 / 改角色；应走个人中心，杜绝「自查自升」与「一键自锁」两条最短路径 |
| 1024 | `PROTECTED_ACCOUNT` | 403 | D | 受保护账号不允许停用或删除 | 受保护账号（`admin`）被停用 / 删除；它是「最后一个超管」之外的第二道保险 |
| 1025 | `DEPT_NOT_FOUND` | 404 | E | 部门不存在 | 建号 / 调岗的目标部门不存在或已停用；刷新部门下拉后重选 |
| 1026 | `PERMISSION_NOT_FOUND` | 400 | E | 权限点不存在 | 角色授权提交了权限点全集之外的 ID；刷新权限点树后重选 |
| 1027 | `PRIVILEGE_ESCALATION` | 403 | D | 不能授予超出自身数据范围或权限 | 数据范围非「全部」时：把角色 `data_scope` 改到超过自身、授予自身不具备的权限点、分配自己不持有的角色；**就地提示不跳登录** |
| 1028 | `ADMIN_SELF_LOCKOUT` | 409 | F | 该操作会导致系统无人可管理 | 削空 `SUPER_ADMIN` 的必需管理能力（`system:role:assign-perm` / `system:user:list` / `system:user:assign-role`）、停用 / 删除 / 摘除最后一个可用超管、受保护账号失去超管角色；**须先补位再操作** |
| 1029 | `OLD_PASSWORD_MISMATCH` | 400 | E | 原密码不正确 | 本人自助改密（`PUT /api/v1/auth/password`）时 `oldPassword` 校验失败；**不区分「口令错」与「账号状态异常」之外的任何信息**，就是「再确认没通过」。就地提示并把错误挂到「当前密码」字段，**不跳登录**（会话仍有效，跳登录等于把输错一次放大成强制重认证） |
| 1030 | `PASSWORD_POLICY_VIOLATION` | 400 | E | 新密码不符合安全要求 | 本人自助改密时新口令未过强度策略：长度不在 8~64、未同时含字母与数字、含空白字符、或**与原口令相同**。判定权威在服务端 `PasswordPolicy`（前端表单规则只是提前拦截）；就地提示并挂到「新密码」字段，修正后重试 |
| 1031 | `CHAT_GROUP_MEMBER_REQUIRED` | 400 | E | 群聊至少需要邀请一位成员 | 建群（`POST /api/v1/chat/groups`）时 `memberIds` 为空，或**去重并剔除创建者后为空**（只填了自己也算没有受邀者）。群主由服务端自动入群、不进 `memberIds`，故「只想建个只有自己的群」不被允许——那不是一个群，是一条自言自语；就地提示，让用户补一位成员后重试 |
| 1032 | `CHAT_GROUP_MEMBER_LIMIT` | 400 | E | 群成员数超出上限 | 建群时受邀人数 **+1（群主）** 超过 `SysGroup.MAX_MEMBERS`(500)——上限口径是**群的总人数**而非受邀人数，与单聊/群聊投递侧的 `MAX_FANOUT_RECIPIENTS`(500) 同源（前端弹窗的 `MAX_GROUP_MEMBERS` 是镜像，权威在服务端）；就地提示，让用户减人后重试 |
| 1033 | `CHAT_GROUP_MEMBER_INVALID` | 400 | E | 邀请的成员不存在或不可用 | 建群时某位受邀成员在 `UserLookupPort#existsActiveUser` 判定下不存在（含已逻辑删除）或已停用。与单聊发送前的用户可用性判定**同一把尺子**：放行会造出「名字挂在群里、却永远读不到消息」的僵尸成员，且事后无人能判断该不该清理；整体回滚（不留半个群），就地提示让用户移除该成员后重试。**不逐位回报是哪一个**——那会把建群端点变成账号存在性枚举器 |
| 1034 | `CHAT_RECALL_EXPIRED` | 400 | E | 消息发出已超过 2 分钟，无法撤回 | 撤回（`POST /api/v1/chat/messages/recall`）时该逻辑消息的**最早一行**已超出 `ChatService.RECALL_WINDOW`(2 min)。窗口是产品口径（给「手滑发错」留改正时间，不给「翻旧账」留通道），故为**终态错误**：重试不会有不同结果，前端就地提示并撤下撤回入口。判定权威在服务端——前端 `isRecallable` 只控制菜单显隐，并留 30s 钟差容忍，**越窗点击仍应按本码提示而不是静默失败** |
| 1035 | `CHAT_RECALL_NOT_FOUND` | 400 | E | 消息不存在或不是你发送的，无法撤回 | 撤回时按 `(sender_user_id, client_msg_id)` 定位不到任何行（消息不存在 / 已逻辑删除 / 不是会话消息），**或该逻辑消息的发送人不是当前用户**。四种情况**合并为一个码**：分开报会给出「这条 `clientMsgId` 是否存在」的探测面，而撤回只能作用于自己的消息，入参是否有效对调用方没有可操作的区别；就地提示 |
| 1036 | `CHAT_QUOTE_TARGET_INVALID` | 400 | E | 引用的消息不存在或已被撤回 | 发送（`POST /api/v1/chat/messages`）时 `quoteClientMsgId` 非空但指向的消息**不在本会话内**、不存在，或**已被撤回**（正文已清空）。引用一条已撤回的消息只会渲染出一个空白引用块，故在写入前拒绝；就地提示并清掉引用条，让用户改引另一条重发 |
| 1037 | `CHAT_GROUP_NOT_FOUND` | 404 | E | 群聊不存在或已解散 | 群管理端点（详情 / 改名 / 邀请 / 移除 / 退群 / 解散）按 `groupId` 查 `sys_group` 时查不到，或该群已停用（解散）。**「不存在」与「已解散」合并为一个码**：分开报会给出「这个群 ID 曾经存在吗」的探测面，而对调用方而言可操作的动作完全相同（提示并刷新会话列表）；就地提示 |
| 1038 | `CHAT_GROUP_ADMIN_REQUIRED` | 403 | D | 你在该群的权限不足 | 群内**身份不足**：改名 / 邀请要求**群主或管理员**、移除 / 解散要求**群主**。与权限点（1003）是**两条正交的授权线**——权限点回答「这个账号有没有群管理这项功能」，本码回答「我在**这个群**里是什么身份」：功能给了、身份不够，仍然拒绝。前端**不跳登录、不清令牌**（会话未失效），面板保持打开状态（换一个有身份的账号或让群主操作即可）；**服务端是权威**，前端 `ability` 只控制按钮显隐 |
| 1039 | `CHAT_GROUP_OWNER_CANNOT_QUIT` | 403 | D | 群主不能退出群聊，请先解散 | 群主试图退群（`POST /groups/{groupId}/quit`），**或**被移除（`DELETE /groups/{groupId}/members/{userId}` 的 `userId` 是群主本身，含「群主移除自己」）。**这两条路必须堵死**：群主退出或移除自己会造出一个**没有所有者的群**——此后无人能改群名 / 邀请 / 移除 / 解散，群变成只能发消息的死结构。群主想离开只能先解散；就地提示 |
| 1040 | `CHAT_GROUP_MEMBER_NOT_FOUND` | 404 | E | 该成员不在群里 | 移除成员时 `userId` 在 `sys_group_member` 里没有生效行（从未入群、已被移除、或已自行退群）。移除是**幂等意图**但对象已不存在：不报成功（否则前端会以为「刚移掉的这个人还在」），也不报 500；就地提示并刷新群详情即可 |
| 1041 | `CHAT_GROUP_OWNER_REQUIRED` | 403 | D | 仅群主可执行该操作 | 移除成员 / 解散群聊的**身份门槛是群主**，而操作者只是管理员或普通成员。与 1038 分开的理由：1038 是「群主或管理员」这档，管理员满足；本码是**只有群主**这档，管理员也不满足——两者合并会让界面上「管理员为什么能改名却不能移除人」无从解释；前端据此显隐（`ability.canRemoveMember` / `canDissolve`），**不跳登录** |

> ⚠️ **1029 / 1030 是「本人自助改密」（GAP-03）的配套错误码**，同时是 **GAP-02「停用即时吊销」** 的失败面：
> 改密成功后服务端 `token_epoch + 1` 全端吊销（含发起请求的当前会话），前端须清本地令牌并回登录页；
> 而 1029 / 1030 属**请求被拒、会话未失效**，弹窗必须留在原地让用户修正，**这两个码清令牌就是缺陷**——
> 前端回归护栏在 `web/src/services/auth/api.test.ts`（成功清令牌 / 失败保留令牌成对断言）。
>
> ⚠️ **1020~1028 是「管理面四条红线」的错误码承载**（内置角色保护 / AUDITOR 锁定 / 防提权 / 防自锁）：
> 它们共同回答「管理员能不能把系统管死或把自己升上去」。判定在服务层（`RoleAdminService` / `UserAdminService`），
> 数据层用「V9 不授予 AUDITOR 任何 `system:*`」做双保险——任一层被绕过仍不越权。
> 前端处理均为**策略 D / F**：就地提示，**禁止引导重新登录**。
>
> ⚠️ **1031~1033 是「群聊建群闭环」的错误码承载**（`ChatGroupService#create`）：三者都是**提交被拒**
> （HTTP 400、会话仍然有效），前端**不得清令牌 / 跳登录**，且**建群弹窗必须留在原地**让用户改条件重试
> （与 1029 / 1030 同一处理形态）。前端弹窗的先行校验（群名非空、至少邀请一位成员、人数不超上限）
> 只是**提前拦截**，判定权威在服务端——绕过前端直接调接口同样被 1031~1033 拦住。
> 其中 1032 的上限口径是「**群的总人数（含群主）**」，与投递侧 `MAX_FANOUT_RECIPIENTS`(500) 必须一致；
> 两侧若只改一侧，由 `ChatGroupMemberLimitTest` 断言暴露。
>
> ⚠️ **1034~1036 是「撤回 + 引用回复」的错误码承载**（`ChatService#recall` / `#resolveQuote`）：三者同样都是**提交被拒**
> （HTTP 400、会话仍然有效），前端**不得清令牌 / 跳登录**，就地提示即可（`web/src/utils/result.ts` 统一映射为 `BAD_REQUEST`）。
> 与建群那三个码的区别在「**撤回是终态**」：1034 重试永远失败，故前端在提示的同时必须**撤下撤回入口**
> （气泡上的 `isRecallable` 会因 2 分钟窗口自然失效）；1035 / 1036 则是「改一个条件就能成功」——前者多半是消息已被他人撤走，
> 后者换一条消息引用即可。三者叠加的另一条红线：**前端不预先判定 1034**，窗口的权威判定只在服务端
> （前端留 30s 钟差容忍是为了不误藏入口，不是为了替服务端裁决）。
>
> ⚠️ **1037~1041 是「群管理（群设置面板）」的错误码承载**（`ChatGroupService` 的
> `detail / rename / invite / removeMember / quit / dissolve`）：与 1031~1033 一样都是**请求被拒、
> 会话仍然有效**（HTTP 403 / 404），前端**不得清令牌 / 跳登录**，面板留在原地刷新即可。
> 这五个码要连起来看的是**双授权线**——权限点（1003）论「这个账号有没有群管理这项功能」，
> 1038 / 1041 论「我在**这个群**里是什么身份」，**两者必须同时成立**：功能给了、身份不够照样拒绝
> （反之亦然）。它们与 1003 的处置也不同：1003 是**功能未授予**（换账号或找管理员配权限），
> 1038 / 1041 是**功能有、但这个群里我说了不算**（找群主操作），因此前端把两种情况都渲染成
> 「按钮不出现」而不是「按钮点了报错」——判定依据是服务端下发的 `ChatGroupAbilityVO`
> （`sql/V16` 只发权限点，群内身份由服务端按 `sys_group.owner_user_id` + `member_role` 实时算出，
> **不落第二种「谁是群主」的副本**，否则会出现两处口径）。
> 1039 是唯一一个**纠正动作不落在本次请求上**的码：群主想退群只能先解散——前端据此把
> 「退出群聊」从群主的面板上隐藏（`ability.canQuit=false`），避免给出一个注定失败的按钮。
> 1037 / 1040 则是「对象已不在」类（策略 E）：刷新面板 / 会话列表即可收敛，重试同一请求不会成功。
> ⚠️ **1016 与 1017 的口径刻意不同**：账号名是登录键（`uk_username` 纯列唯一），逻辑删除行仍占名，故查重**必须含删除行**；
> 邮箱允许删除后复用（只查存活行）。把两者写成同一个查询，要么误报冲突、要么撞唯一键。

> ✅ **GAP-02 收口说明（2026-09-20）**：管理面停用原先只递增 `token_epoch` 而未清 Redis 镜像键
> `at:token:access:{userId}`，请求回源时会读到未提交的旧纪元并**自愈回填**，把吊销抹掉（最坏拖到 access TTL 30 min）。
> 现在 `resetPassword` / `changeStatus(停用)` / `deleteUser` 统一改走 `TokenSessionService#revokeAllInCurrentTransaction`
> （`MANDATORY` 参与调用方事务，避免管理面自我持锁），并在**事务提交后**清镜像键，2 分钟窗口不再存在，改为**当场失效**。
>
> ✅ **自助改密（GAP-03）的副作用同理**：`PUT /api/v1/auth/password` 成功（`code=0`）时同样全端吊销——
> 这是**成功路径**而非错误码，前端不得只看 `code=0` 就以为会话仍在，必须清本地令牌并回登录页。

> ✅ **成功路径的副作用也要断言（2026-09-29 补充）**：上表末尾三行是「**成功即触发**」的副作用——
> 核销成功回推取件回执（`9`）、合并成功发布 `TransferCompletedEvent`（`8`）、到期前定时提醒（`4`）。
> 三者一律**与业务同事务落库、异步推送**，且**发送失败不反向阻塞业务**（传输完成提醒发布失败只留痕）；
> 测试须覆盖「通知写库成功 / 推送失败都不影响主流程」这一支，而非只断言「通知到达」。

> ℹ️ **审计不由错误码决定**：是否落审计事件取决于业务动作（PRD §3 US-06 清单），
> 由 Service 层显式写入；错误码仅用于表达对外结果。
