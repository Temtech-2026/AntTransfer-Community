## §1 P-01 虚拟线程（Java 21 + Boot 3.5.14）

**现状**：未启用（§0.1）。工程目标 Java 21，Boot 3.5.14 原生支持，开关零成本，但收益有边界。

**目标**：让 QPS 上限由 Hikari 池与 DB 决定，而非由 200 个 Tomcat 线程决定。

```yaml
# server/at-bootstrap/src/main/resources/application.yml（公共段）
spring:
  threads:
    virtual:
      enabled: true
```

自证生效（压测前跑一次，避免「以为开了」）：

```java
@GetMapping("/v1/debug/thread-info")
public Map<String, Object> threadInfo() {
    Thread t = Thread.currentThread();
    return Map.of("virtual", t.isVirtual(), "name", t.getName());
}
```

```bash
java -Djdk.tracePinnedThreads=full -jar at-bootstrap-1.0.0-SNAPSHOT.jar   # 抓 synchronized 钉住载体
jcmd <pid> Thread.dump_to_file -format=json /tmp/td.json                 # 对比平台线程峰值
```

### ⚠️ 能力边界（避免误判收益）

| 事实 | 影响 | 对策 |
| --- | --- | --- |
| VT 只在**可卸载**的阻塞点让出载体 | **文件 IO 在 JDK 21 不卸载载体**：分片落盘 / 合并会占住载体 | 合并、打包留在**有界平台线程池**（既有 `filePackExecutor` 模式），别指望 VT 提速磁盘链路 |
| 载体池并行度 = vCPU | 并发文件写会打满载体池 | 必要时调 `-Djdk.virtualThreadScheduler.parallelism`，但先量再调 |
| JDK 21 的 `synchronized` 会 pin（JDK 24/JEP 491 才解） | Hikari 等临界区钉住载体 | 新代码用 `ReentrantLock`；压测期开 `tracePinnedThreads`；Hikari 临界区极短，先测 |
| 线程池 + VT ≠ VT | 走固定 `ThreadPoolTaskExecutor` 时池内仍是平台线程 | VT 场景用 `SimpleAsyncTaskExecutor#setVirtualThreads(true)` 或 `Thread.ofVirtual()` |
| `InheritableThreadLocal` | VT **不继承** | 禁止新引入；`RequestContextHolder`/`SecurityContextHolder`/`AuthzContext` 的 THREADLOCAL 语义正常 |
| VT 不解决 DB 连接上限 | 池仍 20，`connection-timeout` 30 s → 大量 VT 排队 30 s 才失败 | 必须配合 P-06，否则表现为 P99 尖刺 |

**验证**：开关前后各跑「🔐 登录」「⬇️ 下载」两轮，记录活跃/载体线程数；若 P95 无改善，说明瓶颈不在线程数，回 P-05/P-06。

## §2 P-02 分片合并零拷贝（含「别做第二次整件拷贝」）

**现状**（§0.2/§0.3）IO 放大账（单个 N 字节文件）：

| 阶段 | 读 | 写 |
| --- | --- | --- |
| 合并（`merge`） | N | N |
| 合并后算摘要（`sha256(merged)`） | N | — |
| 落正文存储（`ingest`） | N | N |
| **合计** | **3N** | **2N** |

**目标**：① 用 `FileChannel` 消除用户态缓冲区往返；② 摘要与合并**同趟完成**，砍掉整趟 N；③ 有条件时省掉落库那一遍（受 §0.4 跨卷限制，需裁决）。

### P-02a 合并 + 摘要一趟做完 + 预分配

```java
/** 合并结果：路径 + 同趟算出的 SHA-256 + 字节数。 */
public record MergedFile(Path path, String sha256, long size) {}

/**
 * 按索引升序拼接分片，<b>同趟计算 SHA-256</b>。
 *
 * <p>为什么不用 {@code FileChannel.transferTo}：摘要必须看到字节本身，而 transferTo 属
 * 内核态搬运、不经用户态缓冲区，无法同时喂 MessageDigest —— 那会逼出「搬运一趟 + 重读一趟」
 * 的老路（即现状）。IO 账：本实现读 N + 写 N 且摘要免费；transferTo 为读 N + 写 N（CPU 更低）
 * + 重读 N 算摘要。SSD 上前者 IO 更少，故选默认；未来若改由存储层负责算哈希，可切 transferTo。</p>
 */
public MergedFile mergeWithDigest(long uploadId, int chunkCount, long expectedSize) {
    Path merged = taskDir(uploadId).resolve(MERGED_FILE_NAME);
    MessageDigest digest = sha256Digest();
    ByteBuffer buffer = ByteBuffer.allocateDirect(MERGE_BUFFER_SIZE);   // 1 MiB 直接缓冲
    try (FileChannel out = FileChannel.open(merged, StandardOpenOption.CREATE,
            StandardOpenOption.WRITE, StandardOpenOption.TRUNCATE_EXISTING)) {

        if (expectedSize > 0) {                       // 预分配：避免边写边扩的 extent 碎片
            out.write(ByteBuffer.wrap(new byte[]{0}), expectedSize - 1);
            out.position(0);
        }
        for (int index = 0; index < chunkCount; index++) {
            Path part = chunkPath(uploadId, index);
            if (!Files.isRegularFile(part)) {
                throw new BusinessException(ErrorCode.CHUNK_MISSING);
            }
            try (FileChannel in = FileChannel.open(part, StandardOpenOption.READ)) {
                buffer.clear();
                while (in.read(buffer) != -1) {
                    buffer.flip();
                    digest.update(buffer.duplicate());   // 摘要吃同一批字节，不额外读盘
                    while (buffer.hasRemaining()) {
                        out.write(buffer);
                    }
                    buffer.clear();
                }
            }
        }
    } catch (IOException e) {
        deleteQuietly(merged);
        throw new BusinessException(ErrorCode.FILE_UPLOAD_FAIL);
    }
    return new MergedFile(merged, HexFormat.of().formatHex(digest.digest()), expectedSize);
}
```

调用侧收敛为一次 IO（`TransferTaskService.merge`）：

```java
// 现状：merge(...) → Files.size(...) → sha256(...) 三处
ChunkStore.MergedFile merged = chunkStore.mergeWithDigest(uploadId, task.getChunkCount(), task.getFileSize());
if (merged.size() != task.getFileSize()
        || !merged.sha256().equals(reportedSha)
        || !merged.sha256().equals(task.getSha256())) {
    throw new BusinessException(ErrorCode.FILE_INTEGRITY_ERROR);   // 语义与清理分支完全不变
}
```

> **语义等价性**：完整性失败仍触发 `deleteTaskDir`（不可续传）、仍走 `markFailed`，与既有分支逐字一致；`sha256(Path)` 保留，因 `chunkStore.sha256(chunkStore.chunkPath(...))` 分片校验仍在用。

### P-02b 合并期并行（可选，默认关）

```yaml
anttransfer:
  transfer:
    merge-parallelism: 1          # 1=顺序（默认）；>1 按分片偏移并行写
    merge-buffer-size: 1048576    # 8 MiB 分片下 1 MiB 足够；过大挤占直接内存
```

要点：每分片独立 `FileChannel` + `write(buffer, offset)` 定位写，offset 由前缀和预先算出；**并行写拿不到顺序摘要**，等于把重读那趟加回来，故仅在「分片数 > 32 且存储为 NVMe」时才值得开；任一分片失败必须取消其余 + 关 channel + 删 merged，禁止留半成品。

### P-02c 砍掉落库时的第二次整件拷贝（需先裁决）

**关键事实（§0.4）**：两个 volume 跨设备，`Files.move` 必然退化为「拷贝 + 删除」，故「合并完直接 rename 进内容寻址路径」**当前卷布局下不成立**。

| 方案 | 做法 | 收益 | 代价 / 风险 |
| --- | --- | --- | --- |
| C1 同卷 | 暂存根与文件存储根放**同一 volume** 不同子目录 | 合并产物 `ATOMIC_MOVE` 直接成为正文，省 1 读 + 1 写 | 暂存盘不再能独立清理/扩容；暂存写满会波及正文盘 |
| C2 流式直写 | **不产生 `merged.bin`**：分片顺序读 → 直接写正文 `.part`，同趟算摘要与总量，校验后原子改名 | 省 1 读 + 1 写 | 破坏「先本地校验再交 ingest」边界；`FileIngestPort` 需扩展「接收暂存路径」语义；`CryptoCodec` 非直通（EE 加密）时必须退回流式拷贝 |

> ⚠️ 二者都触及「文件正文由 at-file 独占写入」的模块铁律与 `FileIngestPort` SPI 契约，**不得由本方案单方面修改**，须先走 `docs/architecture/architecture.md` §4 登记裁决。

### P-02d 写入侧：分片落盘也可少一次（**需推翻一条既有决策，谨慎**）

`spring.servlet.multipart.file-size-threshold: 0` 意味着分片先落 Tomcat 临时文件、再拷进暂存目录（两写）。可选改为与分片同量级：

```yaml
spring:
  servlet:
    multipart:
      # 与 anttransfer.transfer.chunk-size（8 MiB）对齐：8 MiB 以下走内存直写暂存，超过仍落盘。
      file-size-threshold: 8388608
```

> ⚠️ **`application.yml` 第 84-95 行的现有注释明确写了选中 `0` 的理由**：「一律落临时文件，不在内存里缓冲 64 MiB」。也就是说这是一个**有意决策**（当初按 `max-chunk-size` 64 MiB 估算堆占用），不是遗漏。
> 本项若要落地，必须同批改掉那段注释并给出新的堆占用论证，否则等于把注释与配置改到互相矛盾。
> 账：`max-active-tasks: 3` 下 3 × 8 MiB ≈ 24 MiB 可接受；但真实并发上传数由**压测账号数**决定，若放大到 50 则是 400 MiB —— **必须与 P-06 的堆预算联动，否则是用 OOM 换 IO**。默认建议：**先不动**，等 §8 表 D 证明「分片落盘两次写」确实是瓶颈再动。

**验证**：① `ChunkedUploadMergeIntegrationTest` 全绿（缺片 4002 / 篡改 4003 两条必过），补「乱序 / 单片 / 1024 片」边界；② 1 GiB + 8 MiB 分片（128 片）微基准，配 `iostat -x 1` 看 `%util`/`w_await`；③ 端到端记录合并阶段 P95 与容器 `staging-data` 写量（理论降 1N）。

## §3 P-03 线程池参数模型与暂存盘 IO 调优

**现状**：全局**没有任何** Tomcat / 上传 / 合并线程池配置；合并发生在**请求线程内同步执行**，一次合并占住一个 Tomcat 线程整趟读写。唯一的自定义池是打包用的 `filePackExecutor`（core 2 / max 4 / queue 64 / Abort / daemon）——**这是推荐模板**，但它不属于分片上传。

### 参数模型（先算再配）

```text
并发度 = min(
    vCPU × IO系数,                    # SSD 2~4；HDD 0.5~1（随机 IO 会退化）
    暂存盘可用 IOPS / 单任务 IOPS,
    max-active-tasks(3) × 并发用户数,
    Hikari maximum-pool-size,         # 落库阶段要占连接
    Nginx upstream keepalive / 容器连接数
)
```

参考取值（4 vCPU / SSD / 单机）：

| 池 | core | max | queue | 拒绝策略 | 依据 |
| --- | --- | --- | --- | --- | --- |
| 合并 `at-transfer-merge-` | 2 | 4 | 8 | `AbortPolicy` | 重 IO；队列深了只是把「磁盘排队」换成「堆里排队」，还拖长 P99 |
| 打包（既有）`at-file-pack-` | 2 | 4 | 64 | `AbortPolicy` | 保持现状 |
| 下载 / 取件 | 不池化 | — | — | — | 走 P-01 虚拟线程 + stream 透传 |
| 回调 / 通知 | 1 | 2 | 256 | `CallerRunsPolicy` | 允许降级为同步执行，不丢事件 |

### 关键代码

```java
package com.anttransfer.transfer.config;

/**
 * 合并线程池：与请求线程解耦，避免一次合并占住一个 Tomcat 线程整趟读写。
 *
 * <p>与 at-file 的 {@code filePackExecutor} 同款约束：有界队列 + 中止策略 + 守护线程。
 * 核心数刻意 ≤ vCPU 的一半——合并是纯磁盘 IO，超配只会让多任务争抢同一通道，抬高整体 P99。</p>
 */
@Configuration
@EnableAsync
public class TransferSchedulingConfig {

    public static final String MERGE_EXECUTOR = "transferMergeExecutor";

    @Bean(MERGE_EXECUTOR)
    public ThreadPoolTaskExecutor transferMergeExecutor(TransferProperties properties) {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(properties.getMergeCorePoolSize());     // 默认 2
        executor.setMaxPoolSize(properties.getMergeMaxPoolSize());       // 默认 4
        executor.setQueueCapacity(properties.getMergeQueueCapacity());   // 默认 8
        executor.setKeepAliveSeconds(60);
        executor.setThreadNamePrefix("at-transfer-merge-");
        executor.setDaemon(true);                                        // 不阻塞应用退出
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.AbortPolicy());
        executor.setWaitForTasksToCompleteOnShutdown(false);             // 合并可重试，不为它拖住关机
        executor.initialize();
        return executor;
    }
}
```

调用侧要点（`TransferTaskService.merge`）：**CAS 抢占合并权（`STATUS_MERGING`）必须在提交之前完成**，否则并发请求会重复提交同一任务；队列满被 `AbortPolicy` 拒绝时把状态回写为可重试态，而不是留给客户端一个无解释的 500。

> ⚠️ 异步化会改变「合并进度、失败回写、并发取消」的可见时序，**必须同步补齐**「合并中任务被 `DELETE`」的竞态用例（`ChunkedUploadMergeIntegrationTest` 有同类断言可扩展）。属**中风险改造**，排在 P-01/P-02 之后。

### 暂存盘 IO 调优

| 项 | 建议 | 说明 |
| --- | --- | --- |
| 卷 | `staging-data` 独立卷（**已具备**） | 暂存写满不影响正文，清理策略独立 |
| 文件系统 | XFS 或 ext4 默认参数 | XFS 大文件顺序写更稳 |
| 挂载项 | `noatime,nodiratime` | 避免读分片时写 atime，纯赚 |
| 禁用 tmpfs | 暂存可达 GB 级（`max-chunk-count 1024 × 8 MiB = 8 GiB`） | tmpfs 吃内存，直接触发 OOM Killer |
| 宿主内核 | `vm.dirty_ratio=10`、`vm.dirty_background_ratio=5`（默认 20/10） | 避免高并发写下的一次性回写风暴压死 IO |
| 调度器 | NVMe `none`；SATA SSD `mq-deadline`；HDD `bfq` | 一般宿主层设置 |
| fsync | **当前不做 fsync**（仅 `ATOMIC_MOVE`） | 有意的性能换可用性：原子改名 ≠ 落盘；崩溃可能丢最后若干分片，由暂存 TTL 巡检 + 客户端重传兜底。若合规要求「确认收到即不可丢」再加 fsync，且必须量化 P95 代价 |
| 目录布局 | `<stagingRoot>/<uploadId>/<index>.part`（**已具备**） | uploadId 隔离目录，天然避开 ext4 单目录百万文件的性能悬崖 |

**验证**：合并池 `activeCount`/`queueSize`/`completedTaskCount`（无 micrometer → `jcmd` 或临时日志）；`iostat -x 1` 看 `%util` 是否已 100%（压满即磁盘瓶颈，加线程无意义）；对比池化前后**上传链路 P95** 与**登录链路 P95**（验证请求线程是否被还给其他接口）。

## §4 P-04 Redis 缓存与主动失效策略

**现状（已具备，勿重复造）**：Key 的**权威清单**是 `server/at-common/.../constant/RedisKeyConstants.java`（其类注释明示「镜像 system-design §7.1，新增/变更须两处同步」）。已具备：

- `at:perm:{userId}` 权限标识缓存（TTL 30 min，授权变更主动失效，既有 `invalidate()`）；
- `at:rl:{类}#{方法}[:biz]:{维度}` 限流计数（Lua INCR+EXPIRE，Redis 异常降级放行）；
- 票据族：`at:share:ticket:`（访客一次性、`GETDEL` 一次即焚）、`at:file:ticket:`、`at:chatatt:ticket:`、`at:share:pick:`（均为 5 min）；
- 分享侧防御态：`at:share:count:{token}`（下载配额前置闸，**并发扣减仍以 DB 原子 UPDATE 裁决**）、`at:share:lock:{token}`（提取码错 5 次锁 30 min）、`at:share:expire-notify:{shareId}`（幂等）；
- `at:login:fail:{username}`（15 min）、`at:token:access:`（30 min）、`at:token:refresh:`（7 d）、`at:upload:{uploadId}`（24 h）、`at:chat:retention-lock`、`at:ws:*`。

**未配 Lettuce 连接池**（§0.9）。

**两条必须遵守的既有规约**（写在 `RedisKeyConstants` 类注释里，本方案不得违背）：

1. **P-8**：本类只承载「短期可丢失、可自愈」的会话加速/缓存/计数态，**DB 为权威**；吊销、下载次数等正确性裁决一律以 DB 为准 —— 故新增缓存必须能「miss 回源自愈」，不得出现「只有 Redis 才有的关键判定」；
2. **P-6**：**禁止读-改-写**，计数一律 INCR / Lua 原子；新增缓存键**必须登记到 `RedisKeyConstants`**（并同步 `system-design.md` §7.1），不得散落硬编码字符串。

**原则：先定失效点，再决定缓不缓。没有失效点的数据一律不缓存。**

| 目标数据（**均为待新增，须先登记 key 常量**） | 缓存形式 | TTL | 主动失效点（必须有） | 备注 |
| --- | --- | --- | --- | --- |
| 分享链接只读快照 | `at:share:snapshot:{token}` | 5 min | 撤销 / 改下载上限 / 核销成功 / 文件删除 | 刻意与既有的 `at:share:count:` / `at:share:ticket:` 区分命名。**下载次数绝不进缓存**——沿用既有 `at:share:count:` 前置闸 + DB 原子 UPDATE 权威裁决，否则超发 |
| 秒传预检结果 | `at:instant:{sha256}:{size}` | 10 min | 文件删除 / 回收站清空 / 版本替换 | 缓存的是「能否秒传」，漏一次失效 = 秒传到已删文件 |
| 用户/角色/部门元数据 | `at:user:{id}` 等 | 15 min | 用户禁用 / 部门调整 / 角色变更 | 与 `at:perm` **同一失效时机**，避免「权限已撤但姓名还是旧的」错位 |
| 工作台统计（US-11） | ⛔ **本方案不建议缓存** | — | — | 见下方冲突说明 |
| 未读数 | 不缓存列表 | — | — | 高频轮询改「游标 + 增量」，而非缓存整个未读列表 |

### ⚠️ 与既有裁决的冲突（必须登记，不得径自改）

红队已裁决：工作台统计（US-11）由 `TransferStatisticsService` **直读 `sys_operation_log` 单表聚合**，**不另立统计表 / 不用 Redis 计数器**（`docs/architecture/red-team-review.md`、`docs/prd/README.md` §4.2）。

| 路径 | 收益 | 与既有裁决的关系 |
| --- | --- | --- |
| A. 结果短 TTL 缓存（60 s） | 简单、命中率高 | ⚠️ 引入 ≤60 s 统计滞后窗口，需 PRD 接受 |
| B. 汇总表 + 定时/事件更新 | 查询变单行，最省 | ⛔ **直接违背**「不另立统计表」裁决 |
| C. 保持直读，仅补覆盖索引（P-05） | 零语义变更 | ✅ 与裁决一致，**默认先做这条** |

> 结论：本场景默认动作是 **C**；A/B 一律先登记再动。

### 缓存三件套（防穿透 / 防雪崩 / 防击穿）

```java
/** 统一读缓存模板：空值缓存（防穿透）+ TTL 抖动（防雪崩）+ 单飞重建（防击穿）。 */
public <T> T getOrLoad(String key, Duration ttl, Class<T> type, Supplier<T> loader) {
    String cached = redis.opsForValue().get(key);
    if (cached != null) {
        return NULL_SENTINEL.equals(cached) ? null : deserialize(cached, type);
    }
    String lockKey = key + ":lock";
    // 单飞：只让一个线程回源，其余短暂退避后重试读缓存（不可长时间自旋）
    if (Boolean.TRUE.equals(redis.opsForValue().setIfAbsent(lockKey, "1", Duration.ofSeconds(10)))) {
        try {
            T value = loader.get();
            // 抖动 ±20%：避免同一批 key 同时过期造成的集体回源
            Duration jittered = ttl.plusSeconds(ThreadLocalRandom.current().nextLong(-ttl.toSeconds() / 5 + 1,
                    ttl.toSeconds() / 5 + 1));
            redis.opsForValue().set(key, value == null ? NULL_SENTINEL : serialize(value), jittered);
            return value;
        } finally {
            redis.delete(lockKey);
        }
    }
    // 未抢到锁：短暂退避后重试一次，仍 miss 则回源（宁可多打一次 DB，也不要长时间阻塞）
    sleepQuietly(Duration.ofMillis(50));
    String retry = redis.opsForValue().get(key);
    return retry == null || NULL_SENTINEL.equals(retry) ? loader.get() : deserialize(retry, type);
}
```

#### 失效点登记（新增缓存必须在此登记，否则评审不通过）

| 角色 / 权限点 / 授权变更 | `at:perm:{userId}`（既有 `invalidate`）、`at:user:{id}` |

### P-05d 深分页 → 游标 / 书签分页

**为什么必须改**：MyBatis-Plus 的分页插件对每次 `selectPage` 都会**额外发一条 `COUNT(*)`**，且偏移分页 `LIMIT offset, size` 在 `sys_operation_log`（留存 ≥6 个月、量级最大）上会让 MySQL 扫描并丢弃前 offset 行。`pageSize` 上限虽被 `MybatisPlusConfig.MAX_PAGE_SIZE = 100` 收敛，但**页号**无上限，第 1000 页即 offset 10 万。

**键集分页（keyset / 书签）实现要点**：

```java
/** 游标：把「上一页最后一行的排序键」编成不透明串，禁止客户端解析。 */
public record AuditCursor(LocalDateTime logTime, long id) {
    static String encode(LocalDateTime t, long id) {
        return Base64.getUrlEncoder().withoutPadding()
                .encodeToString((t + "|" + id).getBytes(StandardCharsets.UTF_8));
    }
    static AuditCursor decode(String raw) { /* 解析失败 → 抛 PARAM_FORMAT_ERROR(4001) */ }
}

/**
 * 键集分页：无 COUNT 查询，offset 恒为 0。
 *
 * <p>用行构造器比较 {@code (log_time, id) < (?, ?)}：MySQL 与 PostgreSQL 均支持，
 * 且能命中 P-05b 的 {@code (user_id, log_time, id)} / {@code (log_time, id)} 索引，
 * 排序方向与索引方向一致时不产生 filesort。</p>
 */
public CursorPage<AuditLogVO> pageLogsByCursor(AuditLogQueryDTO query, String cursor, int size) {
    assertTimeRange(query);
    int limit = Math.min(Math.max(size, 1), MAX_PAGE_SIZE);      // 复用既有上界 100
    Long userId = resolveUserIdFilter(query);                    // 是否带 user_id 过滤决定用哪个索引

    LambdaQueryWrapper<OperationLog> wrapper = toWrapper(query);
    if (cursor != null) {
        AuditCursor c = AuditCursor.decode(cursor);
        if (userId != null) {
            wrapper.and(w -> w.lt(OperationLog::getLogTime, c.logTime())
                    .or(x -> x.eq(OperationLog::getLogTime, c.logTime()).lt(OperationLog::getId, c.id())));
        } else {
            wrapper.and(w -> w.lt(OperationLog::getLogTime, c.logTime())
                    .or(x -> x.eq(OperationLog::getLogTime, c.logTime()).lt(OperationLog::getId, c.id())));
        }
    }
    wrapper.orderByDesc(OperationLog::getLogTime).orderByDesc(OperationLog::getId);
    // 多取 1 行用于判断「是否还有下一页」，避免再发 COUNT
    wrapper.last("LIMIT " + (limit + 1));

    List<OperationLog> rows = operationLogMapper.selectList(wrapper);
    boolean hasMore = rows.size() > limit;
    List<OperationLog> page = hasMore ? rows.subList(0, limit) : rows;
    String next = hasMore && !page.isEmpty()
            ? AuditCursor.encode(page.get(page.size() - 1).getLogTime(), page.get(page.size() - 1).getId())
            : null;
    return new CursorPage<>(toVOs(page), next, hasMore);
}
```

**API 契约同步（不得只改后端）**：`docs/api/README.md` §3 需新增 `cursor` / `nextCursor` / `hasMore` 三字段说明与「`cursor` 与 `current` 互斥，同时出现以 `cursor` 为准」的优先级规则；`PageResult` 保持不动以便灰度兼容。此改动属**破坏性契约变更预备项**，须登记 `docs/development/AT-DIFF-todos.md`。

**验证**：`EXPLAIN ANALYZE` 前后对比，断言出现 `Using index`（覆盖索引）且 `rows` 不随页号线性增长；压测「🔄 进度轮询 / 审计列表」在第 1 页与第 500 页分别采样 P95。

## §6 P-06 连接池与容器内存匹配

### 现状（§0.8 / §0.9 / §0.11）

`Hikari maximum-pool-size=20`、`connection-timeout=30000`、Lettuce 无池、Dockerfile 固定 `-Xms256m -Xmx512m`、compose 无内存上限 —— **四者互不匹配**：20 个连接在 512 MiB 堆 + 无上限容器里很容易被结果集与直接内存顶到 OOM。

### 配比模型

```text
容器内存 = 堆 + 直接内存 + 元空间 + 线程栈 + 页缓存外的本机开销
堆        ≈ 容器内存 × 60% ~ 70%
Hikari    ≈ min(vCPU × 2 + 1, DB max_connections / 实例数)     # 不是越大越好
Lettuce   ≈ vCPU × 2（池化）或 1（共享连接，需 share-native-connection=false 才用池）
```

参考配比表（单实例）：

| 容器内存 | vCPU | 堆（`MaxRAMPercentage=70`） | Hikari max | Lettuce max-active | 适用 |
| --- | --- | --- | --- | --- | --- |
| 1 GiB | 2 | 700 MiB | 8 | 8 | 开发 / 小规模 |
| 2 GiB | 4 | 1.4 GiB | 12 | 16 | **推荐起步值** |
| 4 GiB | 8 | 2.8 GiB | 24 | 32 | 压测 / 生产 |

> `max-active-tasks: 3` × 并发用户是上传链路的**真实闸门**：若 50 个虚拟用户共享少数账号，多出来的请求在预检阶段就被 4103 拒掉，**不会**打到 Hikari —— 压测账号数必须等于虚拟用户数（三闸门之二）。

| 反模式 | 后果 | 替代 |
| --- | --- | --- |
| `import * as antd from 'antd'` | 破坏 tree-shaking，整包进首屏 | 命名导入 `import { Button } from 'antd'` |

### P-07c gzip / Brotli

后端不动（Spring 侧压缩会与 Nginx 重复），统一在 Nginx 层做。追加到 `deploy/nginx/anttransfer.conf` 的 `server` 块（或 `http` 块全局）：

```nginx
    # ---------- 文本类资源压缩 ----------
    gzip              on;
    gzip_vary         on;                 # 必须：否则 CDN/代理可能把压缩体发给不支持 gzip 的客户端
    gzip_min_length   1024;               # 小于 1 KiB 压缩收益为负
    gzip_comp_level   6;                  # 6 是体积/CPU 的拐点，9 收益极小
    gzip_proxied      any;
    # 只列文本类；png/jpg/woff2 本身已压缩，列入只是白耗 CPU
    gzip_types        text/plain text/css text/xml application/json application/javascript
                      application/xml+rss application/rss+xml font/woff font/ttf
                      image/svg+xml;

    # ---------- 优先发预压缩产物（构建期生成，零运行时 CPU） ----------
    gzip_static       on;                 # 需 ngx_http_gzip_static_module（官方源编译默认含）
    # brotli 需第三方 ngx_brotli 模块（nginx:alpine 官方镜像不含）；
    # 未编译该模块时，下面两行会导致 nginx -t 失败，必须先确认：nginx -V 2>&1 | grep -o brotli
    # brotli            on;
    # brotli_comp_level 5;                # 5 是 brotli 的性价比拐点
    # brotli_static     on;
    # brotli_types      text/plain text/css application/json application/javascript image/svg+xml;
```

构建期预压缩（新增 `web/scripts/precompress.mjs`，在 `max build` 之后执行）：

```js
// 对 dist 下的 .js/.css/.html/.svg 同时产出 .gz 与 .br，交给 nginx 的 *_static 直接命中。
// 好处：运行时零压缩 CPU；坏处：产物目录体积翻倍，需同步 .gitignore / 镜像大小评估。
import { readFile, writeFile, readdir } from 'node:fs/promises';
import { gzipSync, brotliCompressSync, constants } from 'node:zlib';
import { join, extname } from 'node:path';

const DIST = new URL('../dist/', import.meta.url).pathname;
const TARGETS = new Set(['.js', '.css', '.html', '.svg', '.json']);

for (const name of await readdir(DIST, { recursive: true })) {
  if (!TARGETS.has(extname(name))) continue;
  const file = join(DIST, name);
  const buf = await readFile(file);
  if (buf.length < 1024) continue;
  await writeFile(`${file}.gz`, gzipSync(buf, { level: 9 }));
  await writeFile(`${file}.br`, brotliCompressSync(buf, {
    params: { [constants.BROTLI_PARAM_QUALITY]: 11 },   // 构建期可以拉满，运行时才要省 CPU
  }));
}
```

```json
// web/package.json
"build": "max build && node scripts/gen-version.mjs && node scripts/precompress.mjs",
"precompress": "node scripts/precompress.mjs"
```

> ⚠️ `gzip_static` 与 `brotli_static` 命中时会**自动带上** `Content-Encoding` 与 `Vary` 处理，但仅当 `gzip_vary on` 时才稳；`index.html` 已设 `no-store`（§0.14 既有配置），其 `.gz`/`.br` 仍会被 `try_files $uri` 命中，注意别让预压缩文件把 `no-store` 覆盖掉 —— 上线后必须 `curl -H 'Accept-Encoding: br' -I https://host/` 实测响应头。

**验证**：① `npm run analyze` 对比优化前后首屏 chunk 体积；② `curl -H 'Accept-Encoding: gzip, br' -sI https://host/ | grep -i -E 'content-encoding|vary'`；③ Lighthouse（FCP / LCP / TBT / CLS）前后对比，填 §8 表 E。

### 10.2 落地前必须先修正的三处（对 §9「P0 无前置」的修正）

**① P-01 的能力边界漏了下载热路径**
`BandwidthLimiter.reserve()` / `lastTouchedMillis()` 是 `synchronized` 方法（`BandwidthLimiter.java:109` / `:122`），而 `FileDownloadService` 每次读 buffer 都要 acquire 两个桶（`FileDownloadService.java:515-516`）。JDK 21 的 `synchronized` 会 pin 载体线程（JEP 444；JDK 24 / JEP 491 才解），下载并发高时会限制在「载体线程数 ≈ CPU 核数」，**P95 可能不升反降**。§1 只写了「Hikari 临界区极短，先测」，未覆盖此处。
→ 处理：P0-1 上线前把这两处换成 `ReentrantLock`，或至少先做下载场景的 pin 观测。

**② P0-5 是四文件联动，单独改 Dockerfile 比不改更危险**
`MaxRAMPercentage` 读的是 **cgroup 限制**，而 compose 当前**没有任何 `mem_limit`**。只改 `Dockerfile:95` 不改 compose，JVM 会按**宿主机内存**算堆（如 64 GB × 70% ≈ 44 GB）→ 直接与本机其他服务抢内存甚至被 OOM kill，远差于现在的固定 512 MB。
→ 处理：`pom.xml`（`commons-pool2`）+ `application.yml` + `Dockerfile` + `docker-compose.yml` **同批提交、同批部署**。

**③ P0-4 的「可回滚」要降级**
Flyway 迁移无 DOWN（CE 版不支持 undo），且迁移记录写在 `flyway_schema_history`。回滚是「止血级」（手工 `DROP INDEX`）而非「自动级」。
→ 处理：P0-4 单独发布、迁移前备份、预发先验；**不要**与 P0-5 合并成一次发布——否则出问题无法判断是索引还是连接池导致的失败面变化。
